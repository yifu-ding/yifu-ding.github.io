AI Infra 的未来发展

毕业前的一些关于 AI Infra 的阶段性思考，可能比较粗浅和想当然。我会在入职若干个月之后，重新回看这篇文章，并写下新的思考。

一、昨天的 OS，今天的 Infra

1.1 抛弃对规整性的追求

AI Infra 在当下 AI system 里的定位，仿佛曾今操作系统在计算机中的位置。很多技术思想很一致：Paged Attention 像虚拟内存，KV Cache + 分布式 KV + RAG 像多级缓存，Agent + model routing 像 CPU 任务调度，还有抢占、上下文切换、资源隔离、状态恢复……本质很像，有些命名也是一样的。

有人会说，现在的推理框架普遍都更加支持更规整的、可预测的推理时状态。比如模型形状固定、推理复杂度已知、计算图捕获后能复用，更少动态图。因为规整性容易被转换为更高的利用率，可预测的计算通常比不可预测的计算更容易优化，当然是这样，原理上说这就是永恒不变的真理，但局限于此会限制更多可能性。规整性是当前基础设施约束下的阶段性最优，是当前推理框架的舒适区，受到当前基础设施算力限制、芯片架构限制、编译器设计发展现状的限制等等，是当前阶段性的工程最优解，并不代表未来还是这样。

在技术发展的历史中，很多“不可能”只是当时的基础设施尚未成熟。今天一台机器可以同时维护成千上万个线程、连接和异步任务；Scaling 本身也是算力、显存和分布式系统发展演进的产物。同样的，未来基础设施可能会支持更动态的模型推理方式，让 AI 能同时处理大量动态任务，并且可能会有新的任务组织、管理方式，像操作系统管理进程一样，对 request 进行创建、暂停、恢复、调度、迁移和资源隔离。

此外还有一个值得考虑的事情：过去的机器追求规整或者不支持复杂动态行为，可能是硬件限制；但当前 Infra 偏好规整是多方面的约束，比如当前模型设计本身、硬件架构等。任何单点突破都是有价值的。举例来说，大矩阵乘天然更适合规整的 batch 和静态图，于是不论是模型、算法还是底层的研究，大家都不约而同的往这个已被验证的方向演进。但随着基于 Persistent Kernel 的工作越来越多，Flash Attention 让长上下文变得可能， MoE 的稀疏激活和并行流水线，Deepseek 也提出了 Mega-Kernel 让细粒度流水线变高效了，可能未来也会激发更多的动态模型架构设计。所以未来要转变到另一套动态的系统中，需要模型架构本身和基础设施一起变化。

因此，我第一个很直观能想到的是，过去操作系统做过怎样细粒度、全方位、极致优化到今天这个样子，未来 AI Infra 也会。于是可以想见 Infra 的未来形态，比如包括更动态的流水线、更细粒度的任务调度、更 task-specific、基于请求的资源分配、更丰富灵活的异构支持、软硬件+云边端协同。

1.2 从确定性调度到决策系统

AI Infra 的发展或许可以参考 OS、网络、数据库等计算机传统领域的发展规律，但优化目标有一个本质区别。 之前在传统系统中的优化目标是很明确的，包括执行时间更短、recall 精度更高等，这些目标可以用清晰的规则和标准来评判结果，本质原因是传统计算机里的资源是已知的准确数，比如 CPU 频率、内存大小、磁盘大小，每个 task 占多少 CPU 周期和存储，包括返回结果是否正确，都是比较确定的。

但 AI 推理存在资源和结果两边的不确定性。

（1）难以预估一个请求要消耗多少资源。很多复杂 request 可能需要更多时间、更长推理链、更多步工具调用，才能产生高质量回复。比如先进先出、最短作业优先这种单一调度原则在这里就不适用了。因此，在推理过程中同时衡量请求的复杂度，对推理质量做估计和取舍，这是过程的复杂性。

（2）只能估计 AI 输出的质量，很难精确量化单条回复的质量。宏观上来说因为 AI 是模仿人的判断和思维，人是更复杂的，无法仅用规则来概括。由人类视角来定义的话，“智能”是概率性的、连续的、不可精确度量的。而 AI 模型的训练本身需要一个确切的分数，但部分任务中的 reward 很难设计。此外评估本身也会改变系统的行为，观测会让状态坍缩，而坍缩的结果在后续训练中会被作为观测值，于是逐渐产生更大的偏移。

因此，AI 也会变成一个决策系统，而不是单副本的计算系统。 其实当今的“旗舰模型”或许也不能再称为“模型”，比如很多闭源公司只开放 API，一个 fancy 的模型名称背后有复杂的调度路由。我们希望未来 AI 在训练的时候就涵盖决策路径和答案的不确定性。其实现在的世界模型也考虑了这一层不确定性，但距离完全的决策驱动的系统可能还有一些距离。

二、训推是同一个优化问题

2.1 上下游技术的移花接木

很多之前可能更属于 Infra 范围的技术，正在被转移到上游模型训练生产步骤中，尤其是一些有损模型压缩加速技术。我感觉这些技术越往上游移动，模型最终性能的上限越高。其实本质优势有两点：

  1. 训推一致性更好。把可能有损的技术放到训练阶段，把这些技术变成原生的能力，比如 PTQ 变成 QAT，低比特就是原生能力。
  2. 用更低成本做更大模型的训推。

但在下游技术往上游移动的趋势中我还发现了两点：

（1）并不意味着完全移除训练后算法。比如无损加速技术就可以放到 infra 做，还有下游的各类面向具体场景的服务支持。下游 infra 团队需要负责更加特化的模型线上服务和并发推理。上游训练的时候可以考虑吸收一部分有通用规律、能带来通用收益的技术，但不能把所有下游情况和需求都考虑进来，否则会让上游目标矛盾混乱，拖累模型的基本智能，导致性能不理想。

（2）并不一定适用于所有公司，因为这其实是在决定把模型生产的复杂度放到哪个环节。目前各大公司和团队采取这条路经有明显的先后和取舍，可能是因为：

  • 训练成本 带上压缩等优化的 pretrain 比标准训练更难收敛，迭代周期更长；
  • 人才集中 做训推都高效的架构设计，难度比单纯做推理高效更大，需要懂训练动力学又对推理部署效率有准确预估，是略微交叉的，交叉人才有稀缺性，而一些对前沿探索优先级不高、容错比较低的公司，可能无法吸引最聪明的一群人；
  • 发展路径 多数公司没有足够资源去验证架构创新的收益，每个公司愿景和生存方式不同，多数公司的生存是先保证产品和市场，需要考虑成本收益和产品迭代，不太能承担试错风险。ds 是例外，因为他有量化，有成本底气，也可能是因为长期投资有放长线钓大鱼的习惯，总之他们似乎不在乎短期回本。同理其他有别的业务输血的公司更有可能在 AI 方向去做一些收益不明的尝试。但其他一些 AI 独角兽可能不能承受那么长的反馈周期，他们需要定期向投资人画饼。

反过来想，pre-train 技术是否会移到 post-train？ 下面 2.2 提供一种答案：如果说单体模型的智能目前难以突破的话，那就让多模型协作。

2.2 Harness 级训推一致

Andrew Ng 在 WAIC 上说了三条 Scaling 曲线：GPT-3 靠更多参数，DeepSeek R1 靠更长推理 token，现在则靠更多模型之间的协作带来更高智能上限。

Agentic Harness 是多个模型组成的推理系统，也是当前 AI 系统的主流范式。ensemble 其实早就这样在做：多个模型投票或加权，效果通常比单模型好。这个思路现在正在变成基础 Infra 能力，而 Harness 更进一步，不只是多模型，还包括工具链、各种外部资源。Agent 可以自己决定走哪种路径来解决问题，并从报错中思考、重新设计解决思路，已经是在线学习的范畴了。

那么在线学习需要 Infra 做什么支持呢？局限于我目前对 Harness 的粗浅认知，我认为除了模型执行计算之外，收集反馈信号、策略更新、在线决策路径权衡等一整个链路都离不开更好的 Infra。因此，我认为至少包括：

  • 动态任务图调度：任务数量和依赖关系事先未知，调度器需要支持动态队列管理；
  • 异构模型路由：多模型在一个系统中，Router 要根据任务类型、延迟预算、成本和当前负载选择模型，支持模型fallback 和级联；
  • 资源调度分配：多请求并发下的资源额度管理、工具调用配额、子 agent 数量上限、任务级公平调度和抢占等；
  • 面向 Agent 的 Continuous Batching：Agent 的长轨迹使得异步 RL infra 可能是必须，包括异步生产-消费者队列、流式 data buffer 等；
  • 上下文 KV Cache 和状态管理：多 Agent 共享前缀缓存（Prefix Cache）、子 Agent fork 父 Agent 上下文、多级存储 KV Cache、状态恢复、上下文压缩等等；
  • 工具运行时与沙箱（可能更偏系统）：需要容器或轻量 VM 隔离；CPU/内存/网络/执行时间限制；权限控制；Secret 管理；幂等调用；超时重试；结构化 Observation；工具结果缓存。模型推理快不代表系统端到端快，很多 Agent 的主要延迟来自浏览器渲染、代码执行和外部 API 调用。
  • 状态一致性：多个 Agent 并发修改同一资源时，必须有机制防止互相覆盖。

写到这里，这篇文章里写的很多东西也是我最近看到，所以其实现在就在发生。幸运的话过几个月我也会进某家大厂，成为某个愿景的一线成员，感受到真实的上下游和 infra 系统，到时再回来修改其中的内容。
